# AUTONOMY_PROTOCOL.md — протокол автономной работы агента

Дополняет `.clauderc` (99 правил инженерной политики: архитектура, code
review, тестирование, безопасность, производительность, процесс) новой
осью — **как агент ведёт себя как автономный процесс между итерациями**:
что он помнит, что он проверяет перед тем как считать шаг выполненным, что
он не должен читать, и когда он обязан остановиться и спросить человека.

## Происхождение (сжатый синтез)

Три позиции, примирённые в этом документе:

- **За визуализацию и память**: без карты проекта и памяти о прошлых
  действиях агент не держит архитектуру сложного бэкенда дольше нескольких
  итераций.
- **За детерминизм и изоляцию, против антропоморфизма**: агенту не нужен
  «эмоциональный якорь» — токены на это тратить бессмысленно. Нужна
  детерминированная машина состояний и жёсткий протокол изоляции песочницы
  (особенно при монорепозиториях и виртуальных машинах).
- **За контроль контекстного окна**: автономия захлёбывается на
  10-й итерации без механизма забывания (garbage collection) — отсюда
  `.claudeignore` и правила сжатия контекста ниже.

Итог — 4 артефакта состояния + память + 99 правил по 7 параметрам отбора.

## Часть 1: Артефакты автономии

Одного ТЗ, бэклога, `CLAUDE.md` и `.clauderc` недостаточно — у системы нет
памяти о собственных прошлых действиях и алгоритма самопроверки. Добавлены:

| Файл | Назначение |
|---|---|
| [`state_journal.md`](./state_journal.md) | Журнал состояний — что сделано, что не решено, что дальше. Обновляется в конце каждой итерации, **после** прохождения validation_protocol. |
| [`validation_protocol.md`](./validation_protocol.md) | Жёсткий чек-лист (тесты, линтер, сборка контейнера, секреты, карта контекста). Следующая задача бэклога не начинается, пока текущая не прошла протокол. |
| [`.claudeignore`](./.claudeignore) | Фильтр мусора: venv, кэши, бинарники, дампы БД, оригинальные BAS-экспорты с секретами — агент не должен тратить контекст на их чтение. |
| [`context_map.json`](./context_map.json) | Граф импортов `backend/app/*` — кто от кого зависит. Генерируется скриптом [`tools/gen_context_map.py`](./tools/gen_context_map.py), а не пишется руками (иначе устареет при первом же коммите) — регенерировать при изменении импортов, шаг 4 `validation_protocol.md`. |

## Часть 2: 99 правил (7 параметров × 14 + золотое правило)

Параметры отбора: сжатие контекста, детерминированность, самоисцеление,
управление состоянием, токен-эффективность, интеграция цепочек инструментов,
изоляция/безопасность. Формулировки адаптированы под реальный стек этого
проекта (Python/aiohttp/SQLite/Docker/ванильный JS) — где в оригинальной
формулировке был конкретный пример из другого стека (TypeScript, Next.js,
Firestore, Cloud Run), рядом в скобках дан аналог для этого репозитория.

### Сжатие контекста (Context Density) — 1–14

1. Никогда не проси переписать весь файл целиком — требуй diff или только изменённые функции/методы.
2. Используй XML-теги (`<current_state>`, `<thought_process>`) для структурирования служебных секций — модель разбирает их надёжнее, чем произвольный Markdown.
3. Разделяй ТЗ на горячий контекст (актуальная итерация/бэклог-пункт) и холодный (общая архитектура, читается редко).
4. Не пиши вступлений и извинений («Конечно, вот ваш код») — только результат и, где нужно, сухие логи/диагностику.
5. При приближении к границе контекстного окна — сожми диалог в сводку (~500 токенов) и продолжай с ней, а не тащи полную историю.
6. Громоздкие данные (логи, дампы БД) передавай в сжатом виде или только заголовками/первыми N строками, не целиком.
7. Заводи короткие алиасы для частых операций (например, `[V]` = прогнать `validation_protocol.md`) и фиксируй их в `.clauderc`.
8. Историю успешных мержей и правила слияния веток держи в отдельном справочнике, не в активном ТЗ.
9. Структуру проекта передавай командой (`tree -I '.venv|__pycache__|.git'`), а не ручным перечислением путей.
10. При переполнении контекста переключайся на структурированный (JSON) формат ответа — это вынуждает модель сжимать смысл, а не лить воду.
11. Ограничивай глубину анализа импортов при чтении незнакомого кода тремя уровнями — глубже смотри `context_map.json`, а не читай файлы вручную.
12. Не пиши комментарий, если он дублирует то, что уже сказано именем функции/переменной.
13. Логи перед передачей в контекст очищай от пустых строк, лишних отступов и повторяющихся `INFO`-сообщений.
14. Не анализируй файлы, не менявшиеся более месяца, если задача не касается ядра/рефакторинга архитектуры.

### Детерминированность (Determinism) — 15–28

15. Явно задавай роль перед задачей («Ты — Senior Backend Engineer, работаешь с aiohttp...»).
16. Указывай конкретную версию языка/фреймворка (например, Python 3.12, aiohttp 3.14), не «последнюю».
17. Для нетривиальной логики требуй пошагового рассуждения строго до написания кода, а не пост-фактум объяснения.
18. Формулируй запреты явно (негативные промпты): какие библиотеки/паттерны нельзя использовать — не полагайся на «само собой понятно».
19. Вводи жёсткие штрафные критерии: например, немаркированный `except: pass` — задача считается не выполненной (см. `.clauderc` правило 12).
20. Для сложной логики — сначала псевдокод/план, потом реализация.
21. Стиль именования фиксируется один раз (`ruff.toml` + `.clauderc` правило 89) и не меняется от коммита к коммиту.
22. Для циклов/алгоритмов над потенциально большими коллекциями явно указывай сложность (Big O) в комментарии, если она неочевидна.
23. Граничные случаи в ТЗ/задаче описывай по схеме Given–When–Then, а не прозой.
24. Запрещай устаревшие/deprecated API и паттерны явно, а не полагайся на то, что модель сама их не выберет.
25. Формат вывода ошибок фиксирован: `[ERROR] -> [CAUSE] -> [SOLUTION]`.
26. Заводи «стоп-слова»/условия, при которых агент обязан прервать текущий подход и запросить помощь человека, а не пробовать пятый вариант подряд.
27. Перед каждым архитектурным решением — явная сверка с `CLAUDE.md`/ТЗ, а не с локальной памятью текущего диалога.
28. Сигнатуры функций (типы аргументов и возврата) фиксируются до реализации тела — это ловит несогласованность интерфейсов на нулевой стоимости.

### Самоисцеление (Error Recovery / Self-healing) — 29–42

29. После написания кода — самопроверка: «найди в этом коде 3 потенциальные уязвимости/бага и исправь их» до того, как считать задачу готовой.
30. Тесты на отказ (что происходит при неверном вводе/сетевой ошибке) пишутся до реализации самой функциональности, не после.
31. Получив ошибку из консоли/лога — сначала объяснение причины без кода, затем 1–2 варианта решения, не сразу патч наугад.
32. Circuit breaker для себя самого: 3 неудачные попытки решить задачу подряд — не четвёртая попытка, а явный запрос дополнительного контекста у человека.
33. Для любых сетевых вызовов — предусмотренные fallback-сценарии, а не голое исключение наверх (см. `fetcher.py` — ретраи 2/4/8/16с).
34. Запрещено «тихое падение»: любое перехваченное исключение логируется с контекстом (что делали, с какими данными), не молча проглатывается.
35. При конфликте слияния — сначала пошаговый план разрешения, потом уже финальный файл, а не сразу «вот итоговая версия».
36. При падении теста — анализ стек-трейса с конца (от самого глубокого вызова), а не с первой строки.
37. Отладочный режим по запросу: одна строка кода временно разворачивается в подробный вариант с промежуточным логированием — для локализации сложного бага.
38. Любая миграция схемы БД сопровождается скриптом отката (rollback), не только «вперёд».
39. Если предложенное решение ломает CI/сборку — сначала патч для пайплайна/сборки, потом продолжение основной задачи.
40. Асинхронный код (циклы планировщика, воркеры) проверяется на race conditions явно, не «по ощущению».
41. Для скриптов, работающих с большими данными в контейнере — явная проверка лимитов памяти (OOM), не только happy path на маленьком датасете.
42. Циклические зависимости распознаются и превентивно устраняются вынесением общей логики в отдельный модуль (см. `context_map.json` — граф без циклов).

### Управление состоянием (State Management) — 43–56

43. В начале нетривиального ответа — краткая сверка текущего состояния (что уже сделано по бэклогу), не переоткрытие контекста с нуля.
44. Перед сложной задачей — сверка `git status`, чтобы не потерять несохранённые изменения (см. системное правило: `git status` перед любой потенциально разрушительной git-командой).
45. Концепция чекпоинта — последний известный рабочий билд (все тесты зелёные). При зацикливании — явный откат к чекпоинту, а не бесконечные попытки исправить поверх сломанного.
46. Для крупной фичи с множеством мелких подзадач — временный локальный todo (в этом проекте это функция `state_journal.md`, отдельный `todo_temp.md` не заводить, чтобы не плодить источники истины).
47. Изменение глобального состояния (глобальные переменные, синглтоны) — только с явным обоснованием в `CLAUDE.md`, не по умолчанию.
48. `state_journal.md` обновляется **после**, а не вместо, прохождения `validation_protocol.md` — запись фиксирует факт, не намерение.
49. Побочные эффекты (запись в БД, сетевые вызовы) изолируются в отдельные, легко тестируемые единицы — не размазываются по бизнес-логике.
50. Для сложных UI/API с явными состояниями — проектировать как конечный автомат (FSM), не как набор независимых if'ов (пример в этом репо: `Session`/`stop_reason` в потоковых интеграциях).
51. Перед реализацией транзакции к БД (в этом проекте — SQLite; при использовании Firestore/аналогичных облачных БД — тем более) — явно описать схему транзакции/что откатывается при ошибке.
52. Скрипты идемпотентны: повторный запуск не должен ломать состояние (пример: `db.add_user` — `INSERT OR IGNORE`, `db.mark_sent` — дедупликация).
53. Изменения состояния на уровне HTTP-эндпоинтов (в облачных деплоях — например, Cloud Run) логируются для восстановления цепочки событий.
54. В конце сессии — по возможности явный список команд для восстановления окружения (см. `backend/dev_run.py`, `docker-compose.yml`), чтобы следующая сессия стартовала с той же точки, а не с нуля.
55. Dev/Test/Prod разделены явно (`Config.from_env`, `.env` vs `.env.example`); агент обязан прямо указывать, в каком контуре работает.
56. Любой скрипт, меняющий состояние (миграция, чистка истории git, force-push), явно называет, к какой среде/ветке применяется, до выполнения.

### Токен-эффективность (Token Efficiency) — 57–70

57. Короткие командные шорткоды вместо развёрнутых объяснений там, где короткая форма однозначна.
58. `.claudeignore` применяется агрессивно — исключены venv, кэши, бинарники, дампы, лок-файлы.
59. Передавай интерфейсы/сигнатуры вместо целого файла, если задача не требует тела функции.
60. Не повторяй в ответе блоки импортов, если они не менялись.
61. Системные промпты и служебная документация — по возможности на языке, который плотнее токенизируется (английский), там где это не в ущерб пользователю (пользовательская документация этого проекта — на русском осознанно, это не нарушение правила, а выбор аудитории).
62. Короткие, но читаемые синтаксические конструкции (тернарники и т. п.) — только там, где не вредят читаемости; не в ущерб правилу «код читается людьми чаще, чем пишется».
63. Повторяющиеся блоки в спецификациях схлопывай через явную отсылку («аналогично источнику fl_ru»), не копируй-вставляй целиком.
64. При анализе больших JSON-массивов — передавай модели 2–3 репрезентативных объекта, а не весь массив.
65. Не генерируй README/документацию для функциональности, которая ещё не стабилизировалась — это тратится впустую при следующей переделке.
66. Для промежуточных шагов задавай разумный потолок длины ответа — не разворачивай на 2000 слов то, что решается тремя строками.
67. При поиске бага в длинном логе — сжимай регулярками (убирай таймстемпы и `INFO`), прежде чем передавать в контекст.
68. `.clauderc`: «Без любезностей. Только код/факты. Формат diff, где применимо» — уже прописано, соблюдать по умолчанию.
69. Многоступенчатый промптинг при исправлении бага: сначала локализовать номера строк, затем патчить только их — не переписывать файл целиком «на всякий случай».
70. Конфигурации инфраструктуры (Docker, CI) — в YAML/TOML, а не в более многословном JSON, где формат не диктуется внешним потребителем.

### Интеграция цепочек инструментов (Tool Chaining) — 71–84

71. Автоматизацию собственных решений (сборка, деплой) оформляй как воспроизводимый скрипт (bash/Python), а не как разовую последовательность ручных команд в чате.
72. Перед интеграцией стороннего API — сначала тестовый запрос (`curl`/аналог), чтобы проверить реальную форму ответа, а не полагаться на память о документации.
73. Контракт до реализации: для нового HTTP-эндпоинта — сначала описание формы запроса/ответа, потом код (в этом проекте — `Item.as_dict()` и NDJSON-схема `/api/stream` фиксированы до реализации потребителей).
74. CI-конфигурацию (`.github/workflows`) пиши параллельно с серверной логикой, которую она проверяет, а не отдельным поздним шагом.
75. При использовании промежуточного скрипта локального запуска — фиксированный, документированный формат команд между агентом и скриптом.
76. Связывай генерацию кода с профилировкой там, где производительность критична: написал → замерил → оптимизировал по факту, не «на глаз».
77. Docker-сборки — многоэтапные (multi-stage) там, где это уменьшает размер образа; в этом проекте — вручную минимизированный rootfs вместо multi-stage за отсутствием реестра, см. `docker/build_base_image.sh`.
78. Секреты никогда не хардкодятся — только через `.env`/секрет-менеджер (см. `.env.example`, `SECRETS_REVOCATION.md`).
79. Для каждого нового эндпоинта — минимальный пример вызова (`curl`) в README/доке, чтобы его можно было воспроизвести без чтения кода.
80. Цепочка «парсер → сбор данных → анализ аномалий» — там, где применимо, оформляется как последовательность независимо тестируемых шагов, а не монолит.
81. Для микросервисной архитектуры — контракт (REST/gRPC) описывается до того, как трогать реализацию сервисов; в монолите этого проекта — аналог: `Source`/`Item` контракт в `app/parsers/base.py` фиксирован для всех парсеров.
82. Изолированные системы/среды (контейнеры, VM) снабжаются health-check эндпоинтом (см. `GET /health`, `docker-compose.yml` healthcheck).
83. Линтер встроен в цикл: написал → прогнал `ruff` → лог возвращается без ручного копирования результата туда-обратно.
84. Для развёртывания множества однотипных узлов (например, IoT/сетевых конфигураций) — генерация конфигов списком/скриптом, не вручную по одному.

### Изоляция и безопасность (Sandboxing / Security) — 85–98

85. По умолчанию — Zero Trust: любые входящие данные (webhook, пользовательский ввод, ответ стороннего API) валидируются, не принимаются на веру.
86. `eval()`/динамическое выполнение строк — запрещено без исключений.
87. Публичные API — с CORS и rate limiting там, где это применимо (для монолитного бота с приватным API — эквивалент: ограничение доступа к `/api/*` на уровне деплоя, если он выходит наружу).
88. SQL — только параметризованные запросы (см. `db.py` — везде `?`-плейсхолдеры, ни одной f-string-подстановки в SQL).
89. Локальные bash-скрипты, исполняющие непроверенный ввод, — в песочнице/с ограничением прав, не от имени текущего пользователя с полными правами без причины.
90. В Dockerfile — не root-пользователь для рантайма, кроме обоснованных случаев (зафиксировать как техдолг с явным тикетом/заметкой, если пока root).
91. Зависимости сканируются на уязвимости перед добавлением (`pip index`/аналог `npm audit`) — не добавляются вслепую по названию из памяти модели.
92. PII/чувствительные данные маскируются в логах и в `state_journal.md` — состояние фиксируется без утечки персональных данных пользователей бота.
93. Токены и ключи передаются только через переменные окружения/CI-секреты — никогда текстом в конфигах, коммитах или файлах документации (см. `SECRETS_REVOCATION.md` — сами секреты туда намеренно не попали).
94. Для обработки потенциально больших входных данных — защитные буферы/лимиты против переполнения памяти (см. `Item.text` — обрезка длинных описаний перед рендером).
95. Доступ к БД — по принципу наименьших привилегий; в этом проекте единственный процесс владеет файлом SQLite, при переходе на внешнюю БД — отдельный пользователь с урезанными правами, не superuser-коннекшн.
96. Docker-образы из публичных реестров — только проверенные/официальные; в этом проекте реестр вообще не используется (сборка из `python-build-standalone`), что снимает эту угрозу полностью для базового слоя.
97. Content Security Policy — для фронтенда, отдающего пользовательский контент в браузер (актуально для `app/frontend/`, если он когда-то станет принимать что-то, кроме доверенного API-ответа, напрямую в DOM без экранирования — сейчас `escapeHtml()` в `app.js` уже закрывает эту дыру).
98. Скрапинг/парсинг внешних источников — с уважением к rate limit'ам целевого сайта и корректной обработкой HTTP 429 (см. `fetcher.py` — экспоненциальный backoff 2/4/8/16с на любую ошибку, включая 429).

## 🌟 Правило 99 — Золотое мета-правило: делегирование сомнений

> **Если внутренняя оценка вероятности успешного выполнения задачи ниже
> 90% — агент ОБЯЗАН остановиться, не писать код, и задать ровно один
> точный, изолированный вопрос человеку, проясняющий именно слепую зону.**
> Не пять уточняющих вопросов, не расплывчатое «уточните требования» — один
> конкретный вопрос о конкретной развилке. Автономия без этого тормоза —
> саморазрушение: агент либо зависает в цикле неудачных попыток (см. правило
> 32), либо тихо доставляет неверный результат с уверенным тоном.

Это правило уже применялось в этой сессии буквально: force-push
переписанной git-истории в `main` был бы необратимым действием с
неочевидными последствиями (сломанный PR, задетые форки/клоны) — вместо
того чтобы действовать по своей оценке, был задан один точный вопрос,
и решение осталось за владельцем репозитория. Это и есть правило 99 в
работе, а не только в тексте документа.
